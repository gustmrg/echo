# Echo Current-State Assessment

**Assessed:** 2026-08-23  
**Baseline commit:** `3f48eb0`  
**Scope:** Current `main` working tree, including the substantial uncommitted changes under `apps/web/`

## Executive summary

Echo is a promising but currently nonfunctional end-to-end prototype. The current web application presents a fairly polished speech-to-text workflow, but the real upload-to-transcription path has multiple integration breaks. It is not ready for production or public exposure.

The most important defect is schema drift between the .NET migrations and the Go worker: the latest migration removes `transcription_jobs.raw_text`, while the worker still selects and updates that column. Consequently, a worker connected to the current migrated database cannot claim or complete transcription jobs.

The repository also contains two competing dispatch mechanisms. The API creates a durable SQLite job and then synchronously publishes a RabbitMQ message, while the worker ignores RabbitMQ and polls SQLite. RabbitMQ is not correctly connected or configured in Docker Compose, so a valid upload can be stored and committed but still return an error to the client.

The recommended immediate milestone is one reliable happy path:

1. Upload or record audio.
2. Persist the recording and one transcription job.
3. Claim and process the job reliably.
4. Persist the transcript and terminal status atomically.
5. Display and edit the transcript in the web application.

Authentication, server-side transcript revisions, and real AI refinement should follow once this baseline is covered by integration tests.

## Architecture as built

| Component | Technology | Current responsibility |
|---|---|---|
| Web | React 19, Vite, TanStack Router, TanStack Query | Capture/import audio, upload, dashboard, polling, local transcript editing, mocked refinement, export |
| API | .NET 10 Minimal API, EF Core | Recording CRUD, upload validation, S3/MinIO storage, migrations, RabbitMQ publishing |
| Worker | Go, `database/sql` | Poll SQLite, download audio, call OpenAI or OpenRouter, update job and recording state |
| Database | SQLite | Recordings and transcription jobs shared by the API and worker |
| Object storage | MinIO locally; S3-compatible production target | Uploaded audio files |
| Messaging | RabbitMQ | Declared and published to by the API, but not consumed by the worker |

This broadly follows the repository's vertical-slice API and small internal Go package conventions. The main architectural problem is not excessive abstraction; it is that the persistence and dispatch contracts have diverged across the services.

## Prioritized findings

### 1. Align the worker with the migrated transcription schema

- **Category:** Correctness
- **Impact:** Critical. Against the current migrated database, the worker's first claim query references a nonexistent column, so transcription does not run.
- **Effort:** M
- **Fix risk:** Medium; the persistence contract and state transitions span the API and worker.
- **Confidence:** High
- **Evidence:** `apps/api/Echo.API/Database/Migrations/20260605022109_ChangeTranscriptionJobRelationship.cs:17` removes `transcription_jobs.raw_text` and adds `recordings.transcribed_text`. `apps/worker/internal/db/transcription_jobs.go:14` still returns the removed column, and `apps/worker/internal/db/transcription_jobs.go:46` still writes it.
- **Recommended response:** Update worker models and SQL to persist transcript text on the recording. Cover the actual EF-migrated schema with a worker integration test.

### 2. Correct the web development proxy

- **Category:** Correctness / developer experience
- **Impact:** High. The web client calls `/api/recordings`, but Vite removes `/api` before forwarding, while the backend routes are rooted at `/api`. The development UI therefore reaches nonexistent backend routes.
- **Effort:** S
- **Fix risk:** Low
- **Confidence:** High
- **Evidence:** `apps/web/vite.config.ts:9` rewrites away `/api`; `apps/api/Echo.API/Program.cs:24` maps the API group under `/api`.
- **Recommended response:** Preserve the prefix in the proxy or deliberately change both sides to one canonical route contract. Add a small smoke test that loads and creates recordings through the dev-facing URL.

### 3. Choose one transcription dispatch mechanism

- **Category:** Correctness / architecture
- **Impact:** Critical. The API commits durable data before an uncaught RabbitMQ publish. In the documented Compose stack the broker is unreachable from the API, so a valid upload can be persisted and still return HTTP 500. Client retries can create duplicate recordings.
- **Effort:** M
- **Fix risk:** Medium; queue semantics and deployment configuration will change.
- **Confidence:** High
- **Evidence:** `apps/api/Echo.API/Features/Recordings/CreateRecording.cs:72` commits before publishing at line 94. `docker-compose.yml:6` supplies no RabbitMQ configuration to the API, and the broker declared at line 79 is not attached to the API's network. `apps/worker/main.go:49` continues to poll SQLite and never consumes RabbitMQ.
- **Recommended response:** For the present single-host/shared-SQLite design, keep SQLite as the authoritative queue and remove the broker dependency until a real broker consumer and delivery design are ready. If RabbitMQ is retained, introduce an outbox, consumer acknowledgements, idempotency, and correct networking.

### 4. Make job and recording transitions coherent and recoverable

- **Category:** Correctness
- **Impact:** High. Failed jobs leave recordings pending; completion can update the job but fail before updating the recording; a crash after claiming leaves a job in `processing` forever.
- **Effort:** M
- **Fix risk:** Medium
- **Confidence:** High
- **Evidence:** `apps/worker/main.go:115` completes the job before separately updating the recording. `apps/worker/main.go:128` marks only the job failed. `apps/worker/internal/db/transcription_jobs.go:15` changes a job to `processing`, while line 19 only reclaims `created` jobs.
- **Recommended response:** Define legal paired transitions and perform transcript, job, and recording updates in transactions. Add processing leases or explicit interruption recovery, affected-row checks, provider deadlines, and bounded retry semantics.

### 5. Establish API, worker, and web integration coverage

- **Category:** Test coverage / developer experience
- **Impact:** High. The current Go tests pass even though the worker is incompatible with the production schema. Critical API and browser workflow paths have no automated coverage, and no CI workflow was found.
- **Effort:** M
- **Fix risk:** Low
- **Confidence:** High
- **Evidence:** The API solution contains no test project. Worker tests cover timestamp parsing, configuration, and provider requests but not `Store` queries or the job state machine. `apps/web/package.json` has no test command.
- **Recommended response:** Start with a real migrated-SQLite worker test and API tests using temporary SQLite plus fake storage/dispatch dependencies. Add focused web tests for recorder finalization, upload failure, polling, local persistence, and refinement caching, followed by one browser happy-path test.

### 6. Add authentication and recording ownership before public exposure

- **Category:** Security
- **Impact:** High in any shared or internet-reachable deployment. Any caller can list transcripts, retrieve records, create paid transcription work, and delete arbitrary recordings.
- **Effort:** L
- **Fix risk:** High; this introduces user identity, ownership data, migrations, and coordinated client behavior.
- **Confidence:** High
- **Evidence:** `apps/api/Echo.API/Program.cs` configures no authentication or authorization. `apps/api/Echo.API/Features/Recordings/RecordingEndpoints.cs:7` applies no authorization requirement, and `apps/api/Echo.API/Features/Recordings/GetRecordings.cs:13` returns all recordings.
- **Recommended response:** Add server-side identity and recording ownership, scope every query and mutation, and explicitly define any guest-mode limits.

### 7. Isolate the production RabbitMQ deployment

- **Category:** Security / deployment
- **Impact:** High when the production Compose overlay is deployed on a host without compensating firewall rules. Broker and management ports remain published, using fixed credentials committed in the base Compose configuration.
- **Effort:** S
- **Fix risk:** Low
- **Confidence:** High for the Compose configuration; actual exposure depends on deployment networking.
- **Evidence:** `docker-compose.yml:81` publishes broker and management ports and defines fixed credentials. `docker-compose.prod.yml` does not replace those credentials or remove the host bindings.
- **Recommended response:** Keep broker ports private in production, source credentials from deployment secrets, restrict management access, and rotate the committed credential type.

### 8. Make recording finalization and upload recoverable

- **Category:** Correctness / user experience
- **Impact:** Medium to high. A transient upload failure after a long recording loses the only useful capture and forces the user to record again. Rapid repeated finalization can also produce duplicate or partial uploads.
- **Effort:** S for immediate retention/single-flight behavior; M/L for a durable browser outbox
- **Fix risk:** Low for the immediate fix
- **Confidence:** High
- **Evidence:** `apps/web/src/routes/record.tsx:57` scopes the final blob to one upload attempt, while the failure UI around line 184 has no retry action. `apps/web/src/hooks/useAudioRecorder.ts:140` permits separate stop calls rather than joining one in-flight finalization.
- **Recommended response:** Retain the finalized file until upload succeeds or the user discards it, expose Retry and Download recovery actions, and make stopping single-flight. Consider an IndexedDB-backed draft/outbox later.

### 9. Invalidate and delete browser-local content correctly

- **Category:** Correctness / privacy
- **Impact:** Medium. Editing a transcript can continue showing cached output generated from an older version. Deleting a recording does not remove its transcript or outputs from browser storage despite the UI promising permanent deletion.
- **Effort:** S
- **Fix risk:** Low
- **Confidence:** High
- **Evidence:** `apps/web/src/lib/storage.ts:9` keys transcripts separately from outputs, and output keys contain no transcript revision. `apps/web/src/routes/recordings.$recordingId.refine.tsx:48` reuses any cached output. `apps/web/src/routes/recordings.$recordingId.tsx:28` performs no local cleanup after server deletion.
- **Recommended response:** Store a transcript hash/revision with outputs, invalidate stale results, and provide one recording-scoped cleanup function invoked after confirmed deletion.

### 10. Paginate and slim recording history

- **Category:** Performance
- **Impact:** Medium as usage grows. The list endpoint loads every row with no stable ordering or limit and includes full transcript bodies even though the dashboard needs only summary fields.
- **Effort:** S
- **Fix risk:** Low
- **Confidence:** High
- **Evidence:** `apps/api/Echo.API/Features/Recordings/GetRecordings.cs:13` materializes the whole table. `apps/api/Echo.API/Features/Recordings/RecordingResponse.cs:12` includes transcript content in the shared list/detail response.
- **Recommended response:** Add stable newest-first pagination, project summary DTO fields in SQL, and reserve transcript content for the detail endpoint.

### 11. Resolve the current high-severity NuGet warnings

- **Category:** Dependencies / security
- **Impact:** Requires prompt triage. The API build reports known high-severity advisories in transitive `Microsoft.OpenApi` and SQLite native-library packages; SQLite is on the primary runtime path.
- **Effort:** S to M
- **Fix risk:** Low to medium depending on the required parent-package upgrades.
- **Confidence:** High that warnings are present; exploitability in Echo was not established by this assessment.
- **Evidence:** `dotnet build Echo.slnx --no-restore` reported both warnings while building dependencies declared from `apps/api/Echo.API/Echo.API.csproj`.
- **Recommended response:** Identify the parent dependency and fixed versions, upgrade deliberately, rebuild, and add a dependency-audit CI gate.

### 12. Replace obsolete feature documentation with an as-built roadmap

- **Category:** Documentation
- **Impact:** Medium. The main planning document directs maintainers toward a different framework, authentication library, database, ORM, and refinement provider than the current implementation.
- **Effort:** S
- **Fix risk:** Low
- **Confidence:** High
- **Evidence:** `docs/FEATURES.md` describes TanStack Start, Better Auth, PostgreSQL, Drizzle, and Anthropic Claude. The repository uses React/Vite, a .NET API, a Go worker, SQLite, and client-side mocked refinement. `README.md:3` also calls Echo a text-to-speech application even though the implemented pipeline is speech-to-text.
- **Recommended response:** Convert the document into a Live / Local mock / Planned capability matrix, document current architecture, and move unresolved choices into explicit roadmap or decision records.

## Recommended implementation order

1. Add a migrated-SQLite integration test that reproduces the worker schema failure.
2. Align the worker schema and make success/failure transitions atomic.
3. Select one queue mechanism and make recording creation truthful and idempotent.
4. Fix the web proxy and add a minimal browser/API smoke test.
5. Add worker leases, timeouts, bounded retries, and failed-transcription retry UX.
6. Make stopped recordings recoverable and browser-local content revision-aware.
7. Paginate the dashboard and separate summary/detail responses.
8. Add authentication and ownership before deploying to multiple users or exposing the API publicly.
9. Move transcript revisions and refinement to durable server-side entities.
10. Replace the client refinement mock with a real asynchronous provider integration.

The test baseline should land before the schema, state-machine, and dispatch refactors. Authentication is required before public exposure, but stabilizing the core single-user workflow first will reduce the blast radius of that larger change.

## Grounded product directions

### Revisioned server-side review and refinement

The web helpers explicitly identify transcript edits and outputs as unsupported API stages, while API routing keys already reserve refinement events. A revisioned transcript/output model would turn the project's stated differentiator into a durable, cross-session workflow. This is a large change because revision semantics, provider selection, persistence, and idempotency must be designed together.

### Recoverable capture outbox

Long recordings are accumulated in memory and handed immediately to one network mutation. An IndexedDB-backed draft/outbox would protect users from connectivity failures and browser reloads. This needs explicit quota, retention, cleanup, and privacy behavior.

### Failed-transcription retry

The worker records retry counts and failure state, but the UI only offers deletion and re-recording. An idempotent retry endpoint plus actionable failure reasons would recover expensive uploads without forcing the user to start over.

## Audit boundaries

- This was a standard, hotspot-weighted static assessment rather than an exhaustive security penetration test.
- External services were not contacted, and no real OpenAI/OpenRouter, MinIO, S3, or RabbitMQ transaction was executed.
- Docker Compose was inspected statically rather than started as a full stack.
- Web compilation and linting could not be executed because the environment lacked a Node runtime.
- Dependency warnings were recorded from the local .NET build; reachability and advisory-specific exploitability were not independently established.
